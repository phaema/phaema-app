PHAEMA integrations: market review and plan

2026-11-05 · @Stuart

Summary

Some councils, almost all in mainland Europe, are leaving Microsoft 365 for open-source and European alternatives. In England and Wales, Microsoft 365 will remain the norm for some years. The alternatives councils are moving to are built on open standards: OpenID Connect for sign-in, IMAP and SMTP for email, iCalendar and CalDAV for calendars, WebDAV and WOPI for documents, Matrix for chat, and OGC web services for maps.

So PHAEMA should connect through those standards, not to particular products. One connectors module in the main repository, off by default, would serve councils on Microsoft 365, Nextcloud, openDesk or Google Workspace alike, with each provider just a configuration. The same approach makes PHAEMA's register visible in any GIS, including the open-source QGIS.

Suggested order: standard sign-in; Ordnance Survey address and UPRN lookup with EPC lookup; map layers for GIS; GOV.UK Notify for tenant messages; chat notifications; document storage and editing.

UK position. There is very little movement. The government has a large strategic agreement with Microsoft, and the councils mentioned in reporting have only explored open source on a small scale; this review found no UK council migrating. PHAEMA's customers in England and Wales will mostly keep Microsoft 365 for some years, so it must work well with Microsoft. An open-standards approach also makes PHAEMA attractive to councils considering a move, and to councils elsewhere in Europe.

What PHAEMA already supports

  • Email goes out through any standard mail server (SMTP), whether Microsoft 365, Open-Xchange or the council's own relay.

  • Calendar feed: key dates are published as an iCalendar feed that Outlook, Thunderbird, Nextcloud or any calendar can subscribe to.

  • Open API: a documented REST API (OpenAPI) for properties, titles, leases and parties.

  • Maps: OpenLayers with Ordnance Survey map tiles, falling back to OpenStreetMap; HM Land Registry INSPIRE boundaries can be imported.

  • Spatial database: data is held in PostGIS, which QGIS reads natively.

  • Documents: letters and notices are produced as Word files, which LibreOffice and Collabora also open.

GIS

Councils usually run several GIS products at once. Lincolnshire, for example, lists QGIS (free) alongside ArcGIS, MapInfo and Cadcorp. PHAEMA should not become a GIS; it should make its register appear in whatever GIS the council uses.

  • Publish the register as map layers. Offer OGC API Features and WFS layers for properties, leases, projects and proposed sites. QGIS, ArcGIS, Cadcorp and MapInfo all read these. Each layer follows access areas and project confidentiality, and needs a personal access key.

  • Read-only database views. A council's GIS team can connect QGIS straight to PostGIS views for analysis. This is the cheapest option, but it bypasses PHAEMA's permission checks, so it is for internal GIS teams only, never confidential projects.

  • Ordnance Survey APIs, available to councils through the Public Sector Geospatial Agreement:

    • OS Places: address search and finding the UPRN when adding a property;

    • OS NGD: building footprints and areas to check floor areas and boundaries;

    • vector map tiles for clearer base maps.

  • Planning data. Show constraints such as conservation areas and listed buildings on property and project maps, from the national planning data service. Its terms need checking before this is built.

  • Open-source web mapping. Councils running GeoServer, QGIS Server or Lizmap can show PHAEMA's layers on their own public or internal map sites.

Design: one connectors module

The integrations live in the main repository as one optional module, not in a fork.

  • Off by default. Nothing connects to an outside service until an administrator enters its details and switches it on in Module settings.

  • Each connector switches on separately: sign-in, chat notifications, email filing, calendars, document storage, GOV.UK Notify, Ordnance Survey, EPC and the rest.

  • Providers are configurations. Sign-in is written once for OpenID Connect; Microsoft Entra, Keycloak and Google are settings. The same goes for chat (Teams, Matrix, Nextcloud Talk) and file stores (SharePoint, Nextcloud).

  • Nothing depends on it. Email, PHAEMA passwords and documents stored in PHAEMA stay the defaults, and keep working when a connector is off or the outside service is down.

  • Security. Keys and secrets are set by the installer, never stored in the database. Each connector asks only for the permissions it needs, and every action through a connector appears in the change log.

  • Data stays where it is. PHAEMA stays on UK hosting; documents kept in a council's own file store stay in the council's tenancy.

  • Tested both ways. The automated tests run with each connector on and off.

Priorities

  1. Standard sign-in (OpenID Connect). Most requested by IT teams, and it removes PHAEMA passwords.

  2. OS Places address and UPRN lookup, and EPC lookup. Better data at entry, with free public sources.

  3. Map layers for GIS (OGC API Features and WFS). PHAEMA's register in QGIS, ArcGIS and the rest.

  4. GOV.UK Notify. Texts and letters to tenants at little or no cost.

  5. Chat notifications and approvals. Teams first, then Matrix and Nextcloud Talk.

  6. Document storage and browser editing. SharePoint or Nextcloud, with Collabora or Word online.

  7. Email filing by IMAP, planning data, Companies House, FixMyStreet and BOPS as councils ask for them.
