Architecture overview

PHAEMA is a single server-rendered Django application with a PostgreSQL/PostGIS database and an hourly scheduler, packaged as three Docker containers that each council runs on its own.

Only the reverse proxy faces the network; the web container listens on localhost. The scheduler uses the same image and database as web and also shares the media volume. The browser fetches map tiles directly from Ordnance Survey or OpenStreetMap.

How a request is handled

  1. The browser sends an HTTPS request; the proxy ends TLS and forwards it to Gunicorn on port 8000.

  2. Django middleware runs in order: security headers, WhiteNoise (static files are answered here), sessions, language, CSRF, authentication, messages, clickjacking, then PHAEMA's CurrentUserMiddleware (records who is acting, for the audit trail) and RoleRequiredMiddleware (blocks users with no role).

  3. The URL is routed to an app's view, which checks the user's role and, for changes, can_edit.

  4. The view reads or writes models through the Django ORM; every save or delete of an audited model writes an AuditEntry.

  5. A Django template renders GOV.UK Frontend HTML, or the view returns a file (Excel, CSV, Word, GeoJSON, iCalendar) or JSON for the API.

Data model

PHAEMA holds 119 models (database tables) of business records across fifteen apps, organised around the property and the lease. Every other record hangs off one of those two, and every change is audited.

Cases can also link directly to a property, party or lease event, and jobs to a lease or case; those secondary links are left off the picture.

Key design rules

  • Property hierarchy. A property can be part of another (parent), so a site, building and unit form a tree. Deleting a parent that has children is blocked (PROTECT).

  • Identifiers. reference is the council's own unique asset ID; uprn is an optional Unique Property Reference Number of up to 12 digits.

  • Spatial data. Boundaries are MultiPolygonField in British National Grid (SRID 27700), with easting and northing for a point. INSPIRE parcels are stored separately (InspireParcel) and a surveyor picks parcels on the map to set a property's boundary from them. Geometry is converted to WGS 84 only for the browser.

  • Leases cover several premises. Lease.properties is many-to-many, as titles are to properties.

  • Money is never deleted. Charges, receipts and demand runs use PROTECT, and a credit note is a separate charge pointing at the one it credits. Invoice numbers are unique.

  • Single settings row. ModuleSettings holds the council's switched-on modules and letter details.

  • Audit by signals. AuditEntry uses Django's content types to point at any record, storing the changed fields as JSON.

Scanned documents (OCR, #75)

  • What it does. Any record that saves a PDF in a FileField queues it: a generic post_save receiver (apps/core/ocr.queue_record, connected in CoreConfig.ready) creates a TextCopy row keyed by the stored file name, after the transaction commits. ocr_scans reads waiting rows: pdfminer counts the text on each page; a PDF with text on every page is marked has_text and left alone; otherwise OCRmyPDF (MPL-2.0) runs Tesseract (Apache-2.0) with skip_text, output_type="pdf" and rasterizer="pypdfium", so Ghostscript is not needed. The copy is saved beside the original as <name>.text.pdf, so a confidential project's copy stays under projects/ and is served only by the project pages. The original is never changed.

  • Model TextCopy (migration core.0021): source, status (waiting, done, has_text, too_big, failed), copy, pages, pages_scanned, characters, poor, error, attempts, queued_at, finished_at. A failure is retried up to three times. poor is set when little text was read or under 60% of tokens look like words or numbers. ModuleSettings.ocr_enabled (default on) switches queuing and reading off.

  • Serving. core/views.protected_file and projects/views.project_file call ocr.serving_name(): the viewer and ?raw=1 get the searchable copy, ?download=1 the original, ?download=1&searchable=1 the copy. viewer.scan_state() gives the viewer's note (data-scan).

  • Manage data, Scanned documents (TextCopyAdmin): read only, filter by status, action "Read the selected documents again"; a warning names what is missing when Tesseract or OCRmyPDF is not installed (ocr.missing()). Without them, files stay waiting and nothing else is affected.

  • Install. The Dockerfile installs tesseract-ocr, tesseract-ocr-eng and tesseract-ocr-cym; requirements.txt adds ocrmypdf 17 (which needs Pillow 13). The scheduler loop in docker-compose.yml runs ocr_scans every five minutes between hourly daily_tasks runs. ocr.tidy() removes copies whose original has gone.

  • Demo and tests. demo_media.scanned_pdf makes an image-only counterpart lease on DL-0001. Tests: apps/core/test_ocr.py (13).

Accessibility

PHAEMA targets WCAG 2.2 level AA. GOV.UK Frontend supplies tested components. On top of that:

  • every colour theme and skin was designed to keep text contrast at AA, with a High contrast theme for those who need more;

  • collapsible panels use real buttons with aria-expanded, and closed content is hidden from screen readers as well as from view;

  • maps always have a text alternative (reference, address and grid reference) and nothing depends on the map;

Security

Access is controlled by four roles held as Django groups, with record-level rules for surveyors, and every change to business records is written to an audit trail that cannot be edited.

Authentication

  • Users sign in with a username or an email address, and a password, at /login/. Passwords are stored with Django's default PBKDF2-SHA256 hashing.

  • Password rules: at least 12 characters, not similar to the user's details, not a common password, not all numbers.

  • Sessions use Django's signed session cookie; with DEBUG off, session and CSRF cookies are marked Secure unless SECURE_COOKIES=False (only for local testing over plain HTTP).

  • The API accepts API tokens and the browser session; a username and password (HTTP Basic) only when PHAEMA_API_PASSWORD_SIGN_IN is on. It must only be offered over HTTPS.

  • Two-step sign-in (multi-factor authentication) uses any authenticator app (TOTP, RFC 6238) with single-use recovery codes. A council setting requires it for administrators (the default), for everyone, or makes it optional. The admin site signs in through the same page, and the API refuses a password alone for accounts that use it (API tokens still work for them, as an administrator made the token). Optional single sign-on with the council's own accounts is described below.

Email sign-in is UsernameOrEmailBackend in apps/core/auth_backends.py, the first entry in AUTHENTICATION_BACKENDS. It extends Django's ModelBackend, so permissions are unchanged. The username is tried first; an email address is matched without regard to case and only when exactly one account has it, because Django does not make addresses unique. An unknown name still runs the password hasher, so timing does not show whether an account exists. Two-step sign-in and the API rule apply the same way whichever name is typed. Audit trail

apps/core/audit.py connects to Django's save and delete signals for every business model. Each create, change and delete writes an AuditEntry with the time, the user (from CurrentUserMiddleware), the record and the old and new values. Users see it under Changes (/changes/); there is no screen for editing or deleting entries.

Locked in the database (from 26 November 2026, #94). Migration core.0023_audit_trail_lock adds a PostgreSQL trigger, phaema_audit_guard(), that refuses UPDATE, DELETE and TRUNCATE on core_auditentry, so entries cannot be altered through PHAEMA's database account, including by a bulk QuerySet.delete(). One update is allowed: clearing user_id when a user account is deleted (on_delete=SET_NULL), with every other column unchanged; the entry stays, without the name. Tests: apps/core/test_security_headers.py.

What the lock does and does not do. It protects the log against alteration through the application and its ordinary database connection. It is not absolute: a database superuser, or anyone who can change the schema, can drop or disable the trigger and alter rows, and anyone with the server's files can change the data directly. Councils should restrict and log administrator access to the database server, keep backups (which also hold earlier copies of the log) and keep the server's own logs. Describe the log as protected against ordinary application-level alteration, not as tamper-proof.

Bulk changes (from 26 November 2026, #108). The log is written from model signals, which QuerySet.update(), bulk_update() and bulk_create() do not send. apps/core/audit.py therefore has audited_update(queryset, **changes), which snapshots the records, updates them in one statement and writes an update entry for each record whose values changed, and audited_create(model, items), which writes a create entry for each new record; both do nothing extra for models not registered with the log. They are used for unlinking cases and other records from a project, putting charges into a finance export batch, cancelling an active payment plan, replacing the adopted estate strategy, ticking acknowledgement tasks, the main photo, a property's strategy review date, assigning lease events to the surveyor, ONS index corrections, and the tasks a new case is given. The blank question rows of a new site visit or health check are not logged one by one (the visit or check is), and neither are the API token's last use, retrying text recognition, seed data at install or INSPIRE parcel imports. Use the helpers for any new bulk change to an audited model. Tests: apps/core/test_audit_bulk.py.

Retention purge. The retention schedule suggests keeping change log entries for 7 years. A database administrator removes older ones in a single transaction that switches the lock off for that transaction only:

BEGIN;
SET LOCAL phaema.audit_purge = 'on';
DELETE FROM core_auditentry WHERE timestamp < now() - interval '7 years';
COMMIT;

Take a backup first (./phaema.sh backup), then run it from the PHAEMA folder in docker compose exec db psql -U phaema phaema. The setting ends with the transaction, so the lock is back on at once; the purge itself appears in the PostgreSQL log.

Projects

A Project has a ProjectType (kind, starter phase names, confidential by default), a phase (PHASE_ORDER) and a status; workflow.record_gateway() is the only way to move phase: approved advances (gateway 4 closes), rejected stops. Documents are stored under projects/ and served only by project_file; core/views.protected_file refuses that folder.

Manual steps are CompletionStep rows; automatic steps are computed (a linked property; Property.disposed_on set, which also removes the property from open data). site_from_inspire unions INSPIRE parcels into site_boundary (EPSG:27700); map.geojson returns the site and properties in WGS 84 under the same visibility. Demo projects: apps/projects/demo.py, called by load_demo_data.

Site and buildings. Property holds the physical description of a site or building: location, description, when built, construction, storeys, roof, windows, parking, services and solar panels. The lists of choices are TextChoices on the model; physical_rows() returns the recorded facts as label and value pairs for the property page and reports. Site area is stored in hectares; the admin form (PropertyForm) also takes square metres and converts. Tests: apps/properties/test_site_and_buildings.py.

Site visit sheets. apps/cases/visit.py builds the sheet for a case that has a property (/cases/<id>/site-visit/, Word with ?format=docx): the case, what to know before visiting (from apps/compliance/safety.py, plus the hazards of the buildings within and the current occupiers), the property information, and the checklist. It is read-only: nothing entered on it is saved. Two things are set for each case type. CaseType.visit_parts is the list of property parts to print; the parts are the named sections of apps/properties/report.py (PARTS, sections()), which the property report also uses. CaseTypeChecklistItem rows are the checklist: heading, item, guidance, kind of answer, an optional detail of the property record to print beside it (checks; visit.recorded() reads the value from the property, then what it is part of, then the parts within it) and each_building, which repeats the item under each building of a site. Starting values for the case types PHAEMA ships with are in apps/cases/seed.py and were applied to existing installations by migration cases.0005; a council's later changes are not overwritten. The phone and print layouts are plain CSS on .phaema-sheet in static/css/phaema.css. Tests: apps/cases/test_site_visit.py.

Drag and drop. Every file chooser in the templates is wrapped in the GOV.UK Frontend file upload component (<div class="govuk-drop-zone" data-module="govuk-file-upload">), which lets a file be dropped onto it and falls back to the plain chooser without JavaScript; no other script is involved. A test checks that every chooser is wrapped and has the label the component needs. Three places take several files at once through a multiple input named files: the case page (action file_dropped: .eml and .msg files go through the existing email filing, everything else becomes a CaseDocument), the agreement page (/leases/<id>/files/, PDFs as LeaseDocument of the chosen type) and the property page (/properties/<id>/files/, floor plans or photos). Each file passes the same validators as a single upload and is filed on its own, so one refused file does not stop the others; file_each() in apps/core/files.py applies the limit of 20 files a time and collects the reasons, and title_from_filename() names each record. The pages submit as ordinary forms, so the existing permission checks and CSRF protection apply. Tests: apps/core/test_drag_and_drop.py.

Who may open a file (from 26 November 2026, #108). core/views.protected_file serves /files/<path> only when apps/core/file_access.may_open(user, path) agrees: the person must have a role, the path must belong to a record (it is looked up in every FileField and ImageField), and the record's model must have a rule in file_access.RULES. Core files (property photos and plans, title documents, lease documents, case documents, correspondence, site visit photos) open for everyone with a role, as their records do; maintenance job documents need the maintenance module, compliance certificates and building documents need compliance, and valuation reports and audit evidence need valuations (access.can_use, so the module must be switched on and opened by an access area, or the person is an administrator). Anyone else gets 404, the same as for a missing file. A path held by no record (an import being checked, a searchable copy of a scan) is never served, and project papers are refused here and served by project_file. A model with a file field but no rule is refused; a test (test_every_kind_of_file_has_a_rule) fails until a new one is given a rule. Tests: apps/core/test_file_access.py.

API checks (from 26 November 2026, #108). The property, title, lease and party serializers extend apps/core/api_validation.ModelCleanSerializer, which runs the model's clean() on the record as it would be saved and returns its errors as a 400, so the API applies the same rules as the forms, including "a property cannot be part of itself" round any loop. Property.ancestors(), descendants() and _descendant_ids() also stop at a property they have already seen, so a loop that reached the database some other way cannot make them run forever. Tests: apps/properties/test_api_hierarchy.py, apps/leases/test_api.py.

PDF viewer. PDFs are shown inside PHAEMA with PDF.js, kept in static/vendor/pdfjs/ (the pdfjs-dist package from npm: the library, its worker, the viewer components and their stylesheet and images, character maps, standard fonts and WebAssembly decoders; about 6 MB, no build step, nothing fetched from the internet). No link in the templates changed. The two views that serve files, core/views.protected_file and projects/views.project_file, ask apps/core/viewer.py whether the request is a person opening a page: a GET for a PDF whose Accept header contains text/html and which has no raw or download parameter. If so they return templates/core/pdf_view.html at that same address instead of the file; the page's script (static/js/pdf-view.mjs) then fetches the file from the same address with ?raw=1. Everything else (the viewer's own request, the API, scripts, images, other file types) gets the file exactly as before, and ?download=1 sends it as an attachment. The same permission checks run before either answer, so the viewer opens nothing a person could not already open. Both answers carry Vary: Accept, and the page is no-store. viewer.describe() finds the record that holds the file by looking the stored path up in every FileField, and takes the title, the download file name (the original name where one was kept) and the Back link from it; a file no record holds gets its stored name and a link back to the referring page if that is on the same host. The page works without JavaScript by offering the file to open or download. Scripting inside PDFs, XFA forms and eval are off, and links in a PDF open in a new tab with noopener noreferrer. Password-protected or damaged files show a message and the download link. The strip of small pages is PHAEMA's own code in the same script (the PDF.js package has no thumbnail component): one button per page, each drawn to a small canvas only when it scrolls into view, one at a time, so long documents stay quick; whether the strip is open is remembered in the browser's local storage. To update PDF.js, follow static/vendor/pdfjs/README.md. Tests: apps/core/test_pdf_viewer.py.

Leavers and hand-overs

Administrators use Hand over work (/people/hand-over/, view apps/core/handover_views.py, logic apps/core/handover.py) to move a person's open work to colleagues and, optionally, switch off their sign-in in the same step. Each kind of work is an Item naming its query, the user field it changes and the roles that may receive it: managed properties, open cases, open case tasks, pending case approvals, case contributions, open lease events, open maintenance jobs, pending works-order approvals, open valuation audit queries, projects led, project team places, open project tasks and risks, and supervised staff. Closed and completed records are never changed.

All moves run in one database transaction. Records are saved one at a time, not with a bulk update(), so each change fires the audit signals and appears in the change log under the administrator. Receivers are checked on the server: only active Surveyors and Administrators (and Contributors, for case contributions) are accepted. User accounts are deactivated, never deleted, so names stay on historical records. When adding a model with a user field, add an Item for it in handover.items().

Files

  • Uploaded photos and documents are stored outside the web root and served only through /files/, which needs sign-in.

  • Files are written with permissions 0640; form data other than files is limited to 5 MB per request.

  • Responses carry X-Content-Type-Options: nosniff; only PDF, JPEG and PNG open in the browser, everything else downloads.

Web protections

  • CSRF protection on every form (Django CsrfViewMiddleware).

  • Clickjacking protection: X-Frame-Options: DENY in production.

  • Template auto-escaping against cross-site scripting.

  • The ORM parameterises all database queries.

  • Excel and CSV exports neutralise cells starting =, +, - or @, so a spreadsheet cannot run formulas planted in data.

  • The calendar feed address contains a long random token that acts as its password; users can reset it.

  • Content-Security-Policy on every page (apps/core/security_headers.py, #94): scripts only from PHAEMA itself, plus the two small inline scripts in base.html, which carry a nonce made for each request (request.csp_nonce); no plug-ins (object-src 'none'); no framing (frame-ancestors 'none'); forms post only to PHAEMA; images and map tiles from PHAEMA, OpenStreetMap and Ordnance Survey. Inline style attributes are allowed (they cannot run code). Static files are left out of the policy, because the e-learning page has its own inline script and carries no one's data. PHAEMA_CSP_REPORT_ONLY=True sends the policy without enforcing it; PHAEMA_CSP_IMG_SOURCES, PHAEMA_CSP_CONNECT_SOURCES and PHAEMA_CSP_FORM_ACTIONS add addresses; PHAEMA_CSP_ENABLED=False turns it off.

  • Permissions-Policy turns off camera, microphone, location, payment, USB and serial access; Referrer-Policy same-origin; Cross-Origin-Opener-Policy same-origin.

  • HSTS is sent by PHAEMA as well as the Caddy proxy when DEBUG is off (SECURE_HSTS_SECONDS, one year by default; SECURE_HSTS_INCLUDE_SUBDOMAINS and SECURE_SSL_REDIRECT are off unless set), so councils using their own proxy get it too.

Set at the web server, not in PHAEMA

These should be configured on the reverse proxy in front of PHAEMA (see Deployment):

  • HTTPS with TLS 1.2 or later, and HTTP redirected to HTTPS;

  • Strict-Transport-Security (HSTS);

  • limits on repeated sign-in attempts, or the council's web application firewall;

  • a Content-Security-Policy allowing scripts and styles from the PHAEMA host only (and the OS or OpenStreetMap tile host for maps).

Deployment and operations

In production PHAEMA runs on one UK-hosted Linux server or virtual machine per council, behind an HTTPS reverse proxy, with nightly database backups copied off the server.

Hosting pattern

  1. A Linux server in a UK data centre (council-owned, or a supplier such as IONOS UK cloud).

  2. Docker and the PHAEMA stack as in Installation, with .env set for production.

  3. A reverse proxy (Caddy, nginx or the council's load balancer) that ends HTTPS and forwards to 127.0.0.1:8000. The web port is bound to localhost so it is never exposed directly.

  4. A DNS name such as phaema.example.gov.uk, added to ALLOWED_HOSTS and PHAEMA_BASE_URL.

  5. Outbound SMTP to the council's mail relay or Microsoft 365 for reminders.

One stack per council keeps each council's data in its own database and makes it simple to show where the data lives. Several councils can share one physical host, each in its own stack with its own volumes and secrets.

Backups and restore

  • ./phaema.sh backup writes backups/phaema-YYYYMMDD-HHMMSS.sql.gz with pg_dump. Schedule it nightly with cron and copy the file to separate UK storage.

  • Back up the media volume (photos and documents) on the same schedule, for example with docker run --rm -v phaema-app_media:/m -v $PWD/backups:/b alpine tar czf /b/media.tgz -C /m ..

  • To restore: start an empty stack, then gunzip -c FILE.sql.gz | docker compose exec -T db psql -U phaema phaema, and unpack the media archive into the volume.

  • Test a restore at least every quarter.

Upgrades

./phaema.sh update pulls the latest code, rebuilds and restarts. Migrations run automatically when web starts. Take a backup first. To roll back, check out the previous version with Git (releases are not tagged yet) and restore that day's backup, because migrations are not reversed automatically.

Monitoring

  • /health/ returns success when the app and database answer. Point an uptime monitor at it.

  • ./phaema.sh logs shows Gunicorn, Django and scheduler output. On a server, ship Docker logs to the council's log service.

  • The scheduler container logs each hourly daily_tasks run and each ocr_scans run; a missing daily run means reminders are not going out, and "Not reading scanned PDFs" means Tesseract is missing.

  • All containers restart automatically (restart: unless-stopped).

Scaling

One server with 3 Gunicorn workers suits a single council's estates team. For more users, raise --workers in the Dockerfile command, or move PostgreSQL to a managed UK database service and run more web containers behind the proxy, with media on shared storage.

Testing and quality

PHAEMA has 630 automated tests in 61 files, run on every pull request by GitHub Actions against a real PostGIS database, with a check for missing migrations and Django's deployment checks; a pull request is merged only when they pass. The same workflow audits the Python packages for known vulnerabilities (pip-audit) and builds the container image; CodeQL scans the code weekly and on every pull request, and Dependabot proposes package and action updates each month (CodeQL's two steps as one pull request). From 26 November 2026 (#94) the test job also measures coverage with COVERAGE_CORE=sysmon and fails below 90% (it was 95%), a lint job runs Ruff with the rules in ruff.toml (pycodestyle, Pyflakes, import order, bugbear and Bandit's security rules), and every action is pinned to a commit hash, with the version in a comment. A test (core/test_api_schema.py) builds the OpenAPI description with --validate --fail-on-warn, so a change that makes the API description incomplete fails.

Releases are numbered and published on GitHub. The first is 0.9.0, the last alpha, published on 10 November 2026; beta releases will be numbered from 1.0.0-beta.1 and the first version for live council use will be 1.0.0. The number is held once, as PHAEMA_VERSION in phaema/settings.py, and is shown in the API description. It is changed in the pull request that precedes each release. CHANGELOG.md lists what changed in each release, with anything that needs action under Before updating, and docs/releasing.md gives the numbering rules and the steps (changelog, version, tag, GitHub release, test site, early adopters) and how security fixes go out as patch releases.

REST API

  • Base address /api/, with an OpenAPI 3 schema at /api/schema/ and interactive documentation at /api/docs/.

  • Resources: properties, titles, leases, parties. Results are paged 50 at a time.

  • Authentication by API token (Authorization: Bearer phaema_…), or by session from a signed-in browser; permissions follow the PHAEMA role of the account the token acts for, narrowed by the token (see Security, API tokens). HTTP Basic with a username and password is off unless PHAEMA_API_PASSWORD_SIGN_IN is set.

Extending PHAEMA and contributing

New features are added as Django code in the matching app, with tests, translatable text and an audit registration, and contributed back under AGPL-3.0 with a Developer Certificate of Origin sign-off.

Conventions

  • Every source file starts # SPDX-License-Identifier: AGPL-3.0-or-later.

  • Python follows PEP 8; keep functions small. Business rules live in plain modules beside the models (for example cases/standards.py, compliance/safety.py, core/mywork.py), not in templates.

  • All user-facing text is wrapped in gettext or {% translate %} so a Welsh translation can be added under locale/.

  • Screens follow GOV.UK Design System patterns and the GOV.UK style guide's plain English.

  • Server-rendered pages must work without JavaScript.

Adding a feature: checklist

  1. Add or change models in the right app and run python manage.py makemigrations.

  2. Register new business models with the audit trail in the app's apps.py (audit.register(model)).

  3. Add permissions to the right roles in core/roles.py, and record-level rules to can_edit if surveyors may change it.

  4. Add views, URLs and templates using the shared partials in templates/core/.

  5. Offer Excel and CSV export for any new list (reports/export.py).

  6. Write tests, including the role rules.

  7. Update the help page in apps/help/pages/ and, if screens changed, the training course in training/course.py.

  8. Extend load_demo_data with fictional examples (ZZ postcodes, 9999 UPRNs, ZZ title numbers).

  9. Run the tests and pyflakes, then open a pull request.
