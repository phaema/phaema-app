Architecture overview

PHAEMA is a single server-rendered Django application with a PostgreSQL/PostGIS database and an hourly scheduler, packaged as three Docker containers that each council runs on its own.

Only the reverse proxy faces the network; the web container listens on localhost. The scheduler uses the same image and database as web and also shares the media volume. The browser fetches map tiles directly from Ordnance Survey or OpenStreetMap.

How a request is handled

  1. The browser sends an HTTPS request; the proxy ends TLS and forwards it to Gunicorn on port 8000.

  2. Django middleware runs in order: security headers, WhiteNoise (static files are answered here), sessions, language, CSRF, authentication, messages, clickjacking, then PHAEMA's CurrentUserMiddleware (records who is acting, for the audit trail) and RoleRequiredMiddleware (blocks users with no role).

  3. The URL is routed to an app's view, which checks the user's role and, for changes, can_edit.

  4. The view reads or writes models through the Django ORM; every save or delete of an audited model writes an AuditEntry.

  5. A Django template renders GOV.UK Frontend HTML, or the view returns a file (Excel, CSV, Word, GeoJSON, iCalendar) or JSON for the API.

Technology stack

PHAEMA is a Python 3.12 Django 5.2 application on PostgreSQL 17 with PostGIS, rendered on the server with GOV.UK Frontend. Every component is open source and none needs a paid licence. Data model

PHAEMA holds 56 models (database tables) of business records across eleven apps, organised around the property and the lease. Every other record hangs off one of those two, and every change is audited.

Cases can also link directly to a property, party or lease event, and jobs to a lease or case; those secondary links are left off the picture.

Key design rules

  • Property hierarchy. A property can be part of another (parent), so a site, building and unit form a tree. Deleting a parent that has children is blocked (PROTECT).

  • Identifiers. reference is the council's own unique asset ID; uprn is an optional Unique Property Reference Number of up to 12 digits.

  • Spatial data. Boundaries are MultiPolygonField in British National Grid (SRID 27700), with easting and northing for a point. INSPIRE parcels are stored separately (InspireParcel) and a surveyor picks parcels on the map to set a property's boundary from them. Geometry is converted to WGS 84 only for the browser.

  • Leases cover several premises. Lease.properties is many-to-many, as titles are to properties.

  • Money is never deleted. Charges, receipts and demand runs use PROTECT, and a credit note is a separate charge pointing at the one it credits. Invoice numbers are unique.

  • Single settings row. ModuleSettings holds the council's switched-on modules and letter details.

  • Audit by signals. AuditEntry uses Django's content types to point at any record, storing the changed fields as JSON.

The full field list for every model is in each app's models.py, and the Django admin at /admin/ shows them all.

Front end

Every page is HTML built on the server by Django templates using GOV.UK Frontend components. Every task works without JavaScript; scripts only add conveniences on top.

Templates and styles

  • templates/base.html sets the header, menus, skip link, language and the data-skin, theme and text-size attributes on <html>.

  • Each app has its own template folder; shared pieces live in templates/core/ (form fields, errors, hints, pagination, sortable table headings, download buttons, place filters).

  • static/css/phaema.css holds PHAEMA's own layout; themes.css the colour themes; skins.css the skins.

JavaScript

  • static/js/phaema.js: photo gallery, header menus (one open at a time, Escape closes), and collapsible panels. A panel is section.phaema-panel[data-panel]; the script adds a show/hide button to its heading and remembers closed panels in localStorage under phaema_closed_panels.

  • static/js/phaema-map.js: sets up OpenLayers maps, shows boundaries and lets surveyors draw them. Boundaries are stored in British National Grid (EPSG:27700) and sent to the browser as GeoJSON in WGS 84 (EPSG:4326); the map itself displays in Web Mercator.

  • No framework, bundler or Node.js build is used; files are served as written, with cache-busting names from WhiteNoise.

Accessibility

PHAEMA targets WCAG 2.2 level AA. GOV.UK Frontend supplies tested components. On top of that:

  • every colour theme and skin was designed to keep text contrast at AA, with a High contrast theme for those who need more;

  • collapsible panels use real buttons with aria-expanded, and closed content is hidden from screen readers as well as from view;

  • maps always have a text alternative (reference, address and grid reference) and nothing depends on the map;

  • motion is switched off when the device asks for reduced motion;

  • every page works with a keyboard alone; pages are checked with axe-core during development, with no violations on the main pages. A formal accessibility audit and statement are still to be done.

Security

Access is controlled by four roles held as Django groups, with record-level rules for surveyors, and every change to business records is written to an audit trail that cannot be edited.

Authentication

  • Users sign in with Django's own username and password at /login/. Passwords are stored with Django's default PBKDF2-SHA256 hashing.

  • Password rules: at least 12 characters, not similar to the user's details, not a common password, not all numbers.

  • Sessions use Django's signed session cookie; with DEBUG off, session and CSRF cookies are marked Secure unless SECURE_COOKIES=False (only for local testing over plain HTTP).

  • The API accepts the same session or HTTP Basic authentication (Django REST framework defaults), so it must only be offered over HTTPS.

  • Two-step sign-in (multi-factor authentication) uses any authenticator app (TOTP, RFC 6238) with single-use recovery codes. A council setting requires it for administrators (the default), for everyone, or makes it optional. The admin site signs in through the same page, and the API refuses a password alone for accounts that use it. Single sign-on (for example Microsoft Entra ID) is not built yet; it is the first planned connector.

Roles and permissions

apps/core/roles.py creates or refreshes the groups and their permissions after migrations (ensure_roles).

RoleCan seeCan change

ContributorsEverythingNotes, documents and correspondence on cases they are added to
ViewersEverythingNothing
Signed in with no roleHelp and open data onlyNothing

Three layers enforce this: RoleRequiredMiddleware blocks anyone without a role; Django model permissions decide what kind of record a role may add or change; can_edit(user, obj) decides whether this user may change this particular record. The API applies the same rules through PhaemaPermission.

Audit trail

apps/core/audit.py connects to Django's save and delete signals for every business model. Each create, change and delete writes an AuditEntry with the time, the user (from CurrentUserMiddleware), the record and the old and new values. Users see it under Changes (/changes/); there is no screen for editing or deleting entries.

Access areas and cover

Roles decide what a person can change; access areas (AccessArea, apps/core/access.py) decide which optional modules they can open. Each area lists modules it opens in full, and may grant own_patch_finance (rent ledger and service charges limited to the person's patch) and finance_actions (raise rent, credit notes, finance exports, service charge approvals and finance imports, for Surveyors). Five areas are created by migration core.0013 and every user existing then was added to all of them.

Enforcement is on the server. Every view of an optional module goes through access.module_view(module, off_template), which returns 404 if the council has the module switched off and 403 if the person's areas do not open it, and sets request.access_scope to "full" or "patch". Templates receive modules as ModulesForUser, so every modules.*_enabled test is per person. The patch is computed by patch_people(): the person, everyone below them through StaffProfile.supervisor (the whole chain), and anyone they cover through a current Cover and that person's chain. The same rules apply to lease and party rent panels, dashboards, My work, the report builder (DATASET_MODULES in apps/reports/views.py), the change log (audit_visible), Hand over work receivers and works order approvers. Area membership and cover changes are written to the change log. Tests: apps/core/test_access.py; other tests put new users in every area unless marked own_areas.

Projects

apps/projects holds larger pieces of work with or without properties. A Project has a ProjectType (kind, starter phase names, confidential by default), a phase (PHASE_ORDER) and a status; workflow.record_gateway() is the only way to move phase: approved advances (gateway 4 closes), rejected stops. Visibility is in rules.py: visible(user) filters lists, reports (_project_rows in apps/reports/views.py) and property pages, so confidential projects reach only their team and administrators; _project() in the views returns 404 otherwise and writes a ProjectAccess row for each opening of a confidential project. Documents are stored under projects/ and served only by project_file; core/views.protected_file refuses that folder.

The budget (BudgetLine, BudgetYear) is keyed by the starting year of the April–March financial year (financial_year_of). can_see_budget and can_edit_budget add finance staff through their access areas. importing.SpendWorkbook (Import, Project spending) loads actuals. Cases, jobs and valuations carry a nullable project foreign key; project_for() shows the link only to people who can see the project.

completion.py builds the checklist from delivery onwards. Steps link to admin add or change forms with GET parameters to prefill them; it never writes to the register. Manual steps are CompletionStep rows; automatic steps are computed (a linked property; Property.disposed_on set, which also removes the property from open data). site_from_inspire unions INSPIRE parcels into site_boundary (EPSG:27700); map.geojson returns the site and properties in WGS 84 under the same visibility. Demo projects: apps/projects/demo.py, called by load_demo_data.

Leavers and hand-overs

Administrators use Hand over work (/people/hand-over/, view apps/core/handover_views.py, logic apps/core/handover.py) to move a person's open work to colleagues and, optionally, switch off their sign-in in the same step. Each kind of work is an Item naming its query, the user field it changes and the roles that may receive it: managed properties, open cases, open case tasks, pending case approvals, case contributions, open lease events, open maintenance jobs, pending works-order approvals, open valuation audit queries, projects led, project team places, open project tasks and risks, and supervised staff. Closed and completed records are never changed.

All moves run in one database transaction. Records are saved one at a time, not with a bulk update(), so each change fires the audit signals and appears in the change log under the administrator. Receivers are checked on the server: only active Surveyors and Administrators (and Contributors, for case contributions) are accepted. User accounts are deactivated, never deleted, so names stay on historical records. When adding a model with a user field, add an Item for it in handover.items().

Files

  • Uploaded photos and documents are stored outside the web root and served only through /files/, which needs sign-in.

  • Files are written with permissions 0640; form data other than files is limited to 5 MB per request.

  • Responses carry X-Content-Type-Options: nosniff; only PDF, JPEG and PNG open in the browser, everything else downloads.

Web protections

  • CSRF protection on every form (Django CsrfViewMiddleware).

  • Clickjacking protection: X-Frame-Options: DENY in production.

  • Template auto-escaping against cross-site scripting.

  • The ORM parameterises all database queries.

  • Excel and CSV exports neutralise cells starting =, +, - or @, so a spreadsheet cannot run formulas planted in data.

  • The calendar feed address contains a long random token that acts as its password; users can reset it.

Set at the web server, not in PHAEMA

These should be configured on the reverse proxy in front of PHAEMA (see Deployment):

  • HTTPS with TLS 1.2 or later, and HTTP redirected to HTTPS;

  • Strict-Transport-Security (HSTS);

  • limits on repeated sign-in attempts, or the council's web application firewall;

  • a Content-Security-Policy allowing scripts and styles from the PHAEMA host only (and the OS or OpenStreetMap tile host for maps).

First install

  1. Install Docker and Git (on a Mac: Homebrew, Colima and Docker, as in docs/setup-mac.md).

  2. git clone https://github.com/phaema/phaema-app.git && cd phaema-app

  3. cp .env.example .env and edit it (below). Never commit .env.

  4. ./phaema.sh start — builds the images and waits until /health/ answers.

  5. ./phaema.sh admin — creates the first superuser.

  6. Sign in, open Manage data, Module settings, and switch on the modules the council uses.

  7. Optionally ./phaema.sh demo-data to load the fictional demonstration estate.

Deployment and operations

In production PHAEMA runs on one UK-hosted Linux server or virtual machine per council, behind an HTTPS reverse proxy, with nightly database backups copied off the server.

Hosting pattern

  1. A Linux server in a UK data centre (council-owned, or a supplier such as IONOS UK cloud).

  2. Docker and the PHAEMA stack as in Installation, with .env set for production.

  3. A reverse proxy (Caddy, nginx or the council's load balancer) that ends HTTPS and forwards to 127.0.0.1:8000. The web port is bound to localhost so it is never exposed directly.

  4. A DNS name such as phaema.example.gov.uk, added to ALLOWED_HOSTS and PHAEMA_BASE_URL.

  5. Outbound SMTP to the council's mail relay or Microsoft 365 for reminders.

One stack per council keeps each council's data in its own database and makes it simple to show where the data lives. Several councils can share one physical host, each in its own stack with its own volumes and secrets.

Backups and restore

  • ./phaema.sh backup writes backups/phaema-YYYYMMDD-HHMMSS.sql.gz with pg_dump. Schedule it nightly with cron and copy the file to separate UK storage.

  • Back up the media volume (photos and documents) on the same schedule, for example with docker run --rm -v phaema-app_media:/m -v $PWD/backups:/b alpine tar czf /b/media.tgz -C /m ..

  • To restore: start an empty stack, then gunzip -c FILE.sql.gz | docker compose exec -T db psql -U phaema phaema, and unpack the media archive into the volume.

  • Test a restore at least every quarter.

Upgrades

./phaema.sh update pulls the latest code, rebuilds and restarts. Migrations run automatically when web starts. Take a backup first. To roll back, check out the previous version with Git (releases are not tagged yet) and restore that day's backup, because migrations are not reversed automatically.

Monitoring

  • /health/ returns success when the app and database answer. Point an uptime monitor at it.

  • ./phaema.sh logs shows Gunicorn, Django and scheduler output. On a server, ship Docker logs to the council's log service.

  • The scheduler container logs each hourly daily_tasks run; a missing run means reminders are not going out.

  • All containers restart automatically (restart: unless-stopped).

Scaling

One server with 3 Gunicorn workers suits a single council's estates team. For more users, raise --workers in the Dockerfile command, or move PostgreSQL to a managed UK database service and run more web containers behind the proxy, with media on shared storage.

Extending PHAEMA and contributing

New features are added as Django code in the matching app, with tests, translatable text and an audit registration, and contributed back under AGPL-3.0 with a Developer Certificate of Origin sign-off.

Conventions

  • Every source file starts # SPDX-License-Identifier: AGPL-3.0-or-later.

  • Python follows PEP 8; keep functions small. Business rules live in plain modules beside the models (for example cases/standards.py, compliance/safety.py, core/mywork.py), not in templates.

  • All user-facing text is wrapped in gettext or {% translate %} so a Welsh translation can be added under locale/.

  • Screens follow GOV.UK Design System patterns and the GOV.UK style guide's plain English.

  • Server-rendered pages must work without JavaScript.

Adding a feature: checklist

  1. Add or change models in the right app and run python manage.py makemigrations.

  2. Register new business models with the audit trail in the app's apps.py (audit.register(model)).

  3. Add permissions to the right roles in core/roles.py, and record-level rules to can_edit if surveyors may change it.

  4. Add views, URLs and templates using the shared partials in templates/core/.

  5. Offer Excel and CSV export for any new list (reports/export.py).

  6. Write tests, including the role rules.

  7. Update the help page in apps/help/pages/ and, if screens changed, the training course in training/course.py.

  8. Extend load_demo_data with fictional examples (ZZ postcodes, 9999 UPRNs, ZZ title numbers).

  9. Run the tests and pyflakes, then open a pull request.

Troubleshooting and reference

Most problems come from three settings: ALLOWED_HOSTS, HTTPS cookie and CSRF settings, and email.

Common problems

SymptomLikely causeFix
"Bad Request (400)" on every pageThe host name is not in ALLOWED_HOSTSAdd it to .env, then ./phaema.sh start
Sign-in returns "Forbidden (403) CSRF verification failed" behind HTTPSThe proxy setting is off, so Django sees plain HTTP and the browser's https:// origin does not matchSet BEHIND_HTTPS_PROXY=True and an https:// PHAEMA_BASE_URL, then ./phaema.sh start
Sign-in works over HTTP but the session is lostSECURE_COOKIES=True without HTTPSUse HTTPS, or False only for local tests
"Waiting for PHAEMA to start" never finishesDatabase still starting, or a migration failed./phaema.sh logs, look for the error in web
docker: command not found or cannot connect on a MacColima not runningcolima start
Port 8000 already in useAnother program on 8000Stop it, or change the left-hand port in docker-compose.yml
Reminder emails never arriveEMAIL_HOST blank, so emails go to the logSet the SMTP variables; check scheduler logs
Demo data shows old countsOld code still running./phaema.sh update, then ./phaema.sh demo-data --reset
"Missing staticfiles manifest" outside Docker with DEBUG=FalseNo collectstatic manifestRun python manage.py collectstatic, or use DEBUG=True for the development server
Map shows OpenStreetMap, not OSNo OS key in Module settingsEnter the council's OS Data Hub key
